# The traces list draws its page from Root Spans

`GET /api/traces` is answered in two steps. First it draws the page's trace ids from Root Spans — the spans with no parent — through the partial index `ix_spans_roots (start_time DESC) INCLUDE (service_id, trace_id) WHERE parent_span_id IS NULL`. Only the traces on that page are then aggregated, reached through `ix_spans_trace_id`.

[ADR 0012](0012-the-log-list-is-served-by-a-timestamp-leading-index.md) left this list unmeasured on purpose, and named the reason it could not inherit the log list's fix: grouping by `trace_id` and ordering by `min(start_time)` is an aggregate that `LIMIT` cannot short-circuit. The first production deployment has now measured it. Over a 24-hour window holding **7.1 million spans in 630 187 traces**, one page of a hundred took **13 881 ms**: a parallel index scan reading all 7.1 million rows, a hash aggregate spilling to disk over 630 187 groups, and a top-N sort at the end. The buffer count is the sharper number — `shared hit=2 035 418 read=1 290 545`, some 26 GB of buffer accesses against a window that occupies roughly 3.3 GB on disk. The index scan hands back 7.1 million heap pointers and each one is followed individually; with six Services interleaved inside `(service_id, start_time DESC)` the heap access jumps, and the same blocks are visited again and again. Ten of the fourteen seconds are spent there, before a single group is formed.

No index on `spans` fixes that query, because the cost is not the lookup — it is that a hundred rows are paid for with the whole window. A trace, though, has exactly one span without a parent, so the newest hundred traces *are* the newest hundred Root Spans, and that is an ordered scan the `LIMIT` does stop. At the density measured above the draw reads a hundred index entries instead of 7.1 million rows, and the aggregation that follows sees a hundred traces of some eleven spans each rather than 630 187 traces. The index carries `service_id` and `trace_id` as payload so the draw answers the Source Filter without touching the heap at all, and its filter keeps it to one entry per trace — roughly a thirtieth of the rows a full index over `spans` would hold.

The alternative was a `telemetry.traces` rollup maintained by the write path. It answers more than this does — an error search would become a column rather than a search, and a trace whose Root Span is missing would still be listed — but it costs an upsert on every ingested span, a backfill, retention of its own, and a new failure mode between two tables that must agree. At 630 187 traces a day the partial index reaches the same latency for the common page, so the rollup is not bought yet. The consequences below are the price of not buying it, and the first of them that starts to hurt is what should reopen this.

## Consequences

- **A trace with no Root Span in the draw is no longer listed.** Previously every trace with any span in the window appeared, and its "root" was whichever span sorted first. Now a trace is found through its parentless span, so a trace whose root has not been ingested yet, was never sent, or belongs to a Service outside the Source Filter drops out of the list. It remains reachable by id, and its detail page is unchanged. This is the sharpest edge of the decision: an incoming trace can be briefly invisible in the list while its root is still in flight, and a reader who filters to a downstream Service will not see traces rooted upstream of it.
- **An error search is a search, and says so when it gives up.** `errorsOnly` cannot be answered from a Root Span — whether a trace failed is known only once its spans are aggregated — so the page is filled from a draw a hundred times its size, capped at 20 000 Root Spans. When that draw is spent before the page fills, the answer carries `truncated: true` and the UI says the window was not read to the end, rather than presenting a short list as the whole truth. A window whose errors are rarer than one in two hundred will hit this; a rollup carrying `has_error` as a column is the answer if it becomes the ordinary case.
- Ordering is now by the Root Span's `start_time` rather than by `min(start_time)` across the trace. For a trace whose root begins first — every trace with a clock that agrees with itself — these are the same ordering. Where senders' clocks disagree, the root's own stamp is arguably the better answer; either way the summary's `startTime` still reports `min(start_time)` over the spans read, so the column and the ordering can disagree by the skew.
- The index costs about 56 bytes per trace plus overhead — some 150 MB at three days of the volume above — and one more index to maintain on a table that is written to constantly and never updated. It is the only index on `spans` that a write touches conditionally: a child span does not enter it.
- Building it is a blocking `CREATE INDEX` inside the startup migration, following the precedent of the migrations before it. On a `spans` table of this size that is a pause at startup, not a pause in service, since the Host has not begun listening yet.
- Following [ADR 0009](0009-exploration-reads-the-telemetry-schema-directly.md), the index is added by an Ingestion migration and named for the Exploration query that wants it.
- Measured again on the same deployment once this shipped, the draw that replaced those 13 881 ms plans as an `Index Only Scan using ix_spans_roots` and hands back its hundred rows in **0.457 ms over 56 buffers** — against 3.33 million buffers before. `Heap Fetches: 100` is the visibility map lagging on the newest pages, one fetch per row returned and not worth chasing. Note what the number covers: it is the draw, not the whole page. The aggregation that follows still reads the spans of a hundred traces through `ix_spans_trace_id`, which the endpoint's own timing includes and this measurement does not.
- The index has to exist before any of that is true, and it is built by a migration that runs at startup. The first measurement after this shipped was taken against a server still running the previous image, and duly showed the old plan — `ix_spans_service_id_start_time` with `parent_span_id IS NULL` demoted to a filter, 2.16 million rows per worker thrown away, 9 972 ms. A traces list that is still slow after this decision is a question about which image is running before it is a question about the decision.
