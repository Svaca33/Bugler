# A Fingerprint is distilled from the stack trace, read per Runtime

The kind of trouble a Log Record announces was, until now, the sender's message template — or, where none travelled along, the body with its numbers blanked. That answer is too coarse to be trusted. A production Application was found holding one Episode over a template as generic as "MongoDb transaction commit error", fed by failures with nothing in common but the sentence: different call sites, different causes, one Episode, one verdict. Grouping by what was *said* groups by the sender's choice of words, and a careless word merges unrelated failures for good.

So a Fingerprint is distilled from **the code that threw** rather than the words that reported it. The `exception.stacktrace` attribute is stripped to its frames, normalised, and hashed together with `exception.type`. A Fingerprint Rule, held by the Application, chooses how coarse this is: by the throwing code, by the kind of failure (`exception.type` and the template, ignoring the stack), or by what was said (the old behaviour) — and, above all of them, one optionally named attribute whose value, where a Match carries it, is the whole answer. The Rule is Application-wide and no Service may override it, because an Episode now reaches across Services (ADR 0034) and the two ends must agree on what "the same trouble" means.

**Identity is the frames, never the words.** Hashing `exception.stacktrace` as it arrives would be far worse than the problem being fixed. A .NET stack trace opens with the exception's own message, and the observed one carried a hostname and a transaction number inside it; a Java trace repeats the trick mid-string in every `Caused by:` line. Either would mint a new Fingerprint per occurrence — an Episode per Log Record, an Alert per Log Record. So every line that is not a frame is dropped: headers, `Caused by:`, `... 12 more`, Python's echoed source lines. The cost is the inner exception types, which sometimes discriminate; the outer type survives separately in `exception.type`.

**Line numbers are blanked on purpose.** Every run of digits is emptied before hashing, which erases line numbers along with ports and ids. Keeping them would mean any deploy that shifted a line split one trouble into two, so an Episode could never outlive a release — and outliving releases is the whole point of asking "is it still happening on the version we just shipped". The price is that two `throw` statements in one method become one kind of trouble, and it is worth paying. Runs of identical frames are collapsed for the same reason: recursion of varying depth is one bug, not ten.

**How a stack trace is written is each runtime's own affair**, as the semantic conventions say outright, so the frame recipe is chosen by Runtime — `telemetry.sdk.language`, which every OTel SDK sets and Bugler already stores among the resource attributes. Read rather than registered: a field on the Service would be one more thing to fill in and one more thing to go stale when a service is rewritten, and reading it keeps the whole matter inside Alerting's existing poll (ADR 0010) instead of widening Registry's contract.

The recipes ship for `dotnet`, `java`, `kotlin`, `nodejs`, `webjs`, `python`, `go`, `php` and `ruby`. They differ more than the shared vocabulary suggests: `at` opens a frame in the first five but nowhere else; Go's frames are a function line with a discarded file line under it; PHP names its call after the file position; and in Ruby the **path is the identity**, because a frame named `block in call` says nothing on its own — which is why "drop file paths" is a per-recipe rule and not a global one. `rust`, `erlang`, `cpp` and `swift` are left out: Rust's backtrace format is still an open question upstream, omits file and line without debug information, and carries a per-build symbol hash that would remint the Fingerprint on every deploy; Erlang's is a term rather than lines; and the other two are addresses and mangled names.

**What is not understood coarsens, visibly.** A Runtime with no recipe, a recipe that yields no frames at all, a Match with no stack — each falls one rung down the ladder to `exception.type` and the template, and the Episode records which rung produced it. Nobody ends up worse off than before this decision; the recognised runtimes simply end up better off. A parser written wrong shows up as coarser grouping that somebody can see, never as a plausible fingerprint over nonsense.

## Considered Options

- **The innermost N frames.** Free of configuration and stable across entry points, but the observed failure disproves it: the first frames of every MongoDB error are the driver's own, identical whatever called them. It would have merged exactly the Episodes this decision exists to separate.
- **The culprit — the innermost frame of the Application's own code.** The most precise answer, and the only one that also merges a shared-library bug reached from two different entry points. Rejected because it requires each Application to declare which namespaces are its own: a setting that is empty on day one, wrong after a rename, and impossible to degrade from, since not knowing what is "own code" is indistinguishable from having none.
- **Hashing `exception.stacktrace` whole.** Rejected above — the message text inside it varies per occurrence.
- **A per-Service Runtime field.** Rejected: the sender already declares it, and a declaration that must be maintained by hand is a declaration that will eventually lie.

## Consequences

- A Fingerprint is no longer legible. It becomes a hash, and the readable name moves to the Title, taken once from the opening Match and never used as identity. Anything that showed a Fingerprint to a person must show the Title instead; the MCP tools keep taking the Fingerprint as an opaque token, which suits them better than a sentence did.
- **A shared-library bug reached from two different entry points stays two Episodes.** The frames below the shared code differ, so the hashes differ. This is the accepted cost of refusing the "own code" setting, and it is the one case where the answer is knowably worse than a configured Bugler could give.
- The recipe is versioned and stamped on every Episode. Improving a normaliser re-partitions the space of Fingerprints exactly as changing the Rule does, and both must be legible after the fact rather than silent.
- Changing the Rule mutes the Application's open Logs Episodes and drops the Quiet Window overrides keyed on the old Fingerprints. Muted is the honest end: the watching changed, and nothing is claimed about the problem.
- The poll grows: `exception.type`, `exception.stacktrace`, `telemetry.sdk.language` and `service.version`, against `left(body, 500)` today. A stack trace runs to kilobytes, so the page falls from 5000 rows to 1000 and a stack past 32 kB is read as its first and last 16 kB with the severed line at the seam discarded. Taking only the head would be wrong in both directions at once: .NET puts the throw site first and the Application's own frames after the framework's, while Python puts the innermost frame last and Java appends the root cause at the end.
- Truncation is recorded on the Episode. "Bugler may be grouping this more coarsely than it could" is a thing to be seen rather than guessed at.
- The poll also starts reading `message_template.text`, which Serilog's OTLP sink sends and Bugler ignored — the gap that dropped the observed Application onto the normalised body in the first place.
